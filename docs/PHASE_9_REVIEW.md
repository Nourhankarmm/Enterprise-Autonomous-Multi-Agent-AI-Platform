# Phase 9 — enterprise-login integration and controlled-pilot preparation

The implemented acceptance boundary is an optional, loopback-only Keycloak identity demonstration plus a strict OIDC integration and operator runbook. No actual organization's issuer, domain, MFA policy or deployment has been supplied. Therefore this phase does **not** claim a completed company rollout or production readiness. The executable preflight explicitly records configuration blockers and external verification still required.

## Identity and session behavior

`AUTH_MODE=local` retains the existing synthetic password demo. `AUTH_MODE=oidc` disables that password endpoint and development-token injection. Login uses authorization code, S256 PKCE, a browser-bound one-use state and nonce, fixed callback URI and RSA-signed ID-token validation. Trusted metadata/JWKS/token URLs must remain on the configured issuer origin; only RS256 is accepted. Issuer, audience/authorized party, nonce, expiry, issuance/authentication time and optional configured ACR are checked. Unknown keys are retrieved from the trusted JWKS endpoint, never token-provided URLs. Network responses, timeouts and flow lifetime/count are bounded; failures do not fall back to password login.

Only an operator-created `(issuer, subject)` mapping may log in. There is no just-in-time account creation, email matching, tenant selection from claims, or role import from the provider. Current tenant/role/active state comes from the application database on each request. Provider access/refresh tokens are not stored or returned to frontend JavaScript. The application issues a separate opaque HttpOnly, host-only SameSite=Lax session cookie; it is Secure on HTTPS, expires no later than the verified ID token or one hour, and is stored hashed in the database. Unsafe cookie-authenticated requests require a same-origin CSRF confirmation header. Callback codes/tokens are never placed in app redirect URLs; Uvicorn access logging is disabled to avoid callback-query leakage. Configure ingress logging accordingly too.

Pending flow state/browser/nonce values are hashed; the short-lived PKCE verifier remains in the server flow table until consumption/cleanup because the token endpoint needs it. No authorization code or provider token is persisted. Local and OIDC sessions are method-bound and cannot be used interchangeably. Logout revokes the application session; it does not claim provider-wide SSO logout. Refresh tokens, backchannel provider logout, automatic directory sync and automatic provider-to-application offboarding are not implemented.

## Local identity demonstration

The optional `compose.oidc.yaml` adds pinned Keycloak 26.8.2 with a PKCE-only public demo client, no self-registration and loopback HTTP bindings. The HTTP/backchannel override is allowed only in demo mode; the public issuer remains exact while backend calls use the private Keycloak service. These exceptions are forbidden in restricted mode, which now requires OIDC and a confidential-client secret. The Keycloak development server, HTTP and public demo client must not be exposed publicly. See [Keycloak downloads](https://www.keycloak.org/downloads), [container setup](https://www.keycloak.org/server/containers) and [health probes](https://www.keycloak.org/server/health).

For an interactive synthetic demonstration, install the locked test extras and configure the existing PostgreSQL demo password, then run `python scripts/run_identity_demo.py`. Docker Compose must be installed. The script prompts privately for the local Keycloak administrator password and a synthetic demo-user password, starts the optional stack and prints only its generated username. It does not write passwords to `.env` or files. Keycloak necessarily stores its password hashes/data in its own local volume; its bootstrap administrator credential is passed through the container environment. Reuse the initial admin password when restarting that volume. The launcher leaves containers running for user interaction. Default callback registration supports API ports 8000 and 18000 only; other ports require an explicit matching provider registration.

## Operator identity lifecycle

Migration `0009` adds explicit external identities, one-use flow records and session-method binding; existing local sessions remain local. Back up before upgrading. Use `python -m platform_api.manage create-user` to provision a local tenant/role, then `bind-oidc --username ... --issuer ... --subject ...` to associate the independently verified provider subject. Subjects are not emails. Credentials/claims do not grant authorization. `revoke-sessions` ends application sessions. `disable-oidc` blocks that login binding; `disable-user` additionally removes current application/background authority and revokes sessions. Reactivation requires `activate-user` and explicit binding reactivation; old sessions are not restored. These are privileged host/container CLI operations, not public user-management endpoints.

Provider-only account suspension is not automatically synchronized into application users or already approved background work. Operators must disable the application user for offboarding. This limitation and the chosen MFA/ACR policy require organization-specific review before any real pilot.

## Pilot gate and evidence

Run `python -m platform_api.pilot` for a privacy-minimal configuration report. It exits nonzero and does not emit READY: real issuer ownership/mappings, MFA/offboarding, end-to-end TLS/proxy trust/logging, least-privilege DB roles, production authenticated Temporal, actual backup drills and incident procedures remain external verification gates. `--allow-demo` only permits a CI/demo command exit; it does not change the report into production readiness. Current default/demo PostgreSQL ownership and Temporal development topology remain blockers.

Unit regressions sign actual RSA tokens with an isolated synthetic provider transport and exercise state/nonce/PKCE, signatures/claims, expiry, CSRF, cross-tenant/role escalation, mapping collisions, revoked users/sessions and failure handling. CI repeats on PostgreSQL, then starts actual Keycloak and performs the browser-form authorization-code flow through HTTP, tests unmapped/disabled users, application logout, callback replay, CSRF, operator revocation and provider outage. This is synthetic HTTP protocol acceptance, not a visual browser test or a real company-provider acceptance. CI reports contain booleans/status/versions only, never passwords, codes, tokens or private keys.

Implementation follows [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html), [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html) and [PyJWT verification guidance](https://pyjwt.readthedocs.io/en/stable/usage.html). Those controls reduce defined risks; they do not certify the deployment or automate organization-specific identity governance.
